# Redis WRONGPASS Intermittent Auth Failures on Railway

## Root Cause Analysis

### The Core Problem: Railway Rotates Redis Credentials on Redeploy

Railway's managed Redis service **regenerates the connection password whenever the Redis service is redeployed** (plugin update, infrastructure migration, or manual redeploy). Your backend, however, holds a **hardcoded snapshot** of the old password in `REDIS_URL`.

```
Timeline:
──────────────────────────────────────────────────────────────────
T+0     You copy-paste Redis connection string → REDIS_URL="redis://:abc123@..."
T+Nwks  Railway redeploys Redis (e.g. version bump, infra event)
        → Redis password is now "xyz789"
        → Your REDIS_URL still says "abc123"   ← WRONGPASS begins
T+Nwks  Someone manually redeploys YOUR service, or Railway syncs the reference
        → password re-syncs → health check green again
T+...   Cycle repeats on next Redis redeploy
──────────────────────────────────────────────────────────────────
```

### Why It "Self-Heals"

One of these usually rescues it without anyone understanding why:

1. **You redeploy your backend** (to investigate) → Railway injects the *current* `REDIS_URL` from the reference variable at deploy time → new password baked in → works again
2. **Railway's own infra** eventually restarts your service → same effect
3. Redis connection pool exhaustion causes full reconnect, but the password was already stale — this is a distraction, not the fix

### Why It Recurs

Each Railway Redis redeploy generates a new password. The static copy drifts again.

---

## Confirming the Diagnosis

### Step 1: Check whether you're using a reference or a literal

In Railway dashboard → your backend service → **Variables tab**:

```
# BAD — literal copy-paste (static snapshot):
REDIS_URL = redis://:abc123@containers-us-west-999.railway.app:6379

# GOOD — Railway reference variable (live pointer):
REDIS_URL = ${{Redis.REDIS_URL}}
```

If you see the literal string, that **is** the bug.

### Step 2: Correlate timestamps

```bash
# Pull Railway deployment logs for BOTH services
railway logs --service redis   --since 30d | grep -i "deploy\|restart\|redeploy"
railway logs --service backend --since 30d | grep -i "WRONGPASS\|ReplyError"
```

You will find that every `WRONGPASS` cluster starts within minutes of a Redis service deployment event.

### Step 3: Verify credential drift in-flight (during an incident)

```bash
# Extract password currently in your running container's env
railway run --service backend printenv REDIS_URL
# Compare against what Railway considers the live Redis password
railway run --service redis   printenv REDIS_URL
# They will differ — smoking gun confirmed
```

### Step 4: Check Railway audit log

Dashboard → Project → **Activity** tab. Redis deploy events will align with your incident timestamps.

---

## The Durable Fix

### Fix 1: Use Railway Reference Variables (Primary Fix, 2 minutes)

In your backend service's Variables tab, **delete** the literal `REDIS_URL` and replace it with:

```
REDIS_URL = ${{Redis.REDIS_URL}}
```

Railway evaluates this reference **at each deploy**, injecting the current live credential. When Redis is redeployed and its password rotates, your next backend deploy picks up the new value automatically.

> ⚠️ **Caveat:** This still requires a backend redeploy after a Redis credential rotation. See Fix 2 for runtime resilience.

### Fix 2: Implement Runtime Reconnection with Auth Retry

Your app should not treat auth failure as fatal. Add exponential backoff with credential refresh:

```typescript
// redis-client.ts  (Node / ioredis example)
import Redis from "ioredis";

const MAX_RETRIES = 10;

function createClient() {
  const client = new Redis(process.env.REDIS_URL!, {
    // ioredis retryStrategy covers network drops
    retryStrategy(times) {
      if (times > MAX_RETRIES) return null; // stop retrying, let it throw
      return Math.min(times * 200, 3000);   // backoff up to 3s
    },

    // WRONGPASS is not a network error — handle it explicitly
    reconnectOnError(err) {
      const isAuthError =
        err.message.includes("WRONGPASS") ||
        err.message.includes("NOAUTH") ||
        err.message.includes("invalid password");

      if (isAuthError) {
        // Log with high severity so you're paged
        console.error("[redis] AUTH failure — credential mismatch detected", {
          timestamp: new Date().toISOString(),
          error: err.message,
        });
        // Return 2 = reconnect AND re-send the failed command after reconnect
        // This buys time if Railway is mid-rotation
        return 2;
      }
      return false;
    },
  });

  client.on("error", (err) => {
    console.error("[redis] client error", err.message);
  });

  return client;
}

export const redis = createClient();
```

### Fix 3: Trigger Backend Redeploy Automatically After Redis Redeploy

Use Railway's webhooks to chain deployments:

```bash
# In Railway: Redis service → Settings → Deploy Webhooks

      },

        query: `mutation {
          serviceInstanceRedeploy(serviceId: "${process.env.BACKEND_SERVICE_ID}")
        }`,
      }),
    });
  }
  res.sendStatus(200);
});
```

## Root Cause

Railway periodically **rotates/regenerates credentials** for managed services (Redis, Postgres, etc.). When `REDIS_URL` was set by copy-pasting the connection string, it became a **literal value** stored against your consuming service — a snapshot of the password at that moment in time. When Railway rotates the Redis password, the upstream service gets the new credential immediately, but your literal env var still holds the old password. This produces `WRONGPASS` errors. Eventually (after a redeploy, a manual fix, or another rotation cycle), things realign — hence the "self-healing" — only to break again on the next rotation. The health check appears green by investigation time because the rotation has already cycled past the breakage window.

---

## Confirming It

The tricky part: Railway's GraphQL API returns **resolved values by default**, so a reference like `${{Redis.REDIS_URL}}` and a hardcoded literal look identical when queried normally. You must pass `unrendered: true` to see the raw stored value:

```graphql
{
  variables(
    projectId: "<your-project-id>"
    environmentId: "<your-environment-id>"
    serviceId: "<your-backend-service-id>"
    unrendered: true
  )
}
```

**Interpret the result:**

| What you see in the response | Meaning |
|---|---|
| `${{Redis.REDIS_URL}}` | ✅ Correct — a live reference, resolves on every deploy |
| `redis://default:somepassword@...` | ❌ Literal — a stale snapshot, drift-prone |

If the unrendered value is a `redis://...` string, you've confirmed the bug regardless of whether the password currently matches.

---

## Durable Fix

Replace the literal with a Railway **variable reference** so it re-resolves dynamically on every deploy:

```graphql
mutation {
  variableUpsert(input: {
    projectId: "<your-project-id>"
    environmentId: "<your-environment-id>"
    serviceId: "<your-backend-service-id>"
    name: "REDIS_URL"
    value: "${{Redis.REDIS_URL}}"
  })
}
```

Use your `railway-api-token` (write-scoped) for this mutation. Railway will trigger an automatic redeploy. Verify `/health/ready` shows `redis: true` afterwards.

---

## Why This Is Durable

A reference is **not a value** — it's an instruction Railway evaluates fresh at deploy time against the current upstream service definition. No matter how many times Railway rotates the Redis password, your service always receives the current credential. The drift vector is eliminated structurally rather than patched.

---

## Broader Audit

This is a class of bug, not a one-off. Audit every service that consumes another service's generated credential:

- Check all `*_URL`, `*_PASSWORD`, `*_HOST` vars across all services/environments with `unrendered: true`
- Any that return a literal connection string rather than a `${{Service.VAR}}` reference should be converted
- Apply this to all Railway projects (RCC, ComoxCoach, etc.) — same failure class, same fix

**The rule:** any time a service consumes a credential *generated by* a sibling Railway service, use `${{ServiceName.VAR_NAME}}` — never copy-paste.
```

# Diagnosing Sentry Source Map Upload for React Native (EAS + Hermes)

## Why You Don't See a Mobile Release in the Releases List

This is a **very common confusion**. React Native source maps uploaded via `@sentry/react-native` do **not** necessarily create a visible "Release" in the Sentry Releases UI the same way a backend deploy does. Here's what's actually happening:

---

## How React Native Sentry Releases Actually Work

```
Backend:           my-api @ abc123def    ← git SHA, shows in Releases list
React Native:      com.myapp@1.2.3+42   ← bundleId@version+buildNumber
                                           ← only appears AFTER a crash/event is received
```

**The release entry is created lazily** — Sentry only shows it in the Releases list once at least one event has been associated with it, OR if the `sentry-cli` upload explicitly creates it.

---

## Step 1: Verify the Upload Actually Happened

### Check EAS Build Logs Directly

Look for these specific log lines in your EAS build output:

```bash
# Good signs — what you want to see:
> sentry-cli releases files com.myapp@1.2.3+42 upload-sourcemaps ...
> Source Map Upload Report
>   Minified Scripts
>     ~/index.android.bundle (sourcemap at ~/index.android.bundle.map)
>   Source Maps
>     ~/index.android.bundle.map

# Bad signs:
> warning: no projects associated with release
> error: API request failed
> SENTRY_AUTH_TOKEN is not set  ← even if you think it is
```

### Use sentry-cli to Query Directly

```bash
# Install sentry-cli locally if needed
npm install -g @sentry/cli

# List all releases for your org — including ones with no events
sentry-cli \
  --auth-token $SENTRY_AUTH_TOKEN \
  releases \
  --org your-org-slug \
  --project your-project-slug \
  list

# Check files uploaded to a specific release
sentry-cli \
  --auth-token $SENTRY_AUTH_TOKEN \
  releases \
  --org your-org-slug \
  --project your-project-slug \
  files "com.myapp@1.2.3+42" list
```

**If the release exists but has no files listed, the upload failed silently.**
**If the release doesn't exist at all, the upload never ran.**

---

## Step 2: Confirm What Release String Your App Is Using

The release name must **exactly match** between what was uploaded and what the SDK reports at runtime.

```typescript
// In your Sentry.init() — check this value
Sentry.init({
  dsn: '...',
  release: 'com.myapp@1.2.3+42', // must EXACTLY match upload
  dist: '42',                      // must EXACTLY match --dist flag used in upload
});
```

### The Hermes-Specific Wrinkle

With Hermes, you have **two separate bundles** (Android has both `index.android.bundle` and potentially a Hermes bytecode artifact). Verify your `sentry.gradle` or upload script targets the right one:

```groovy
// android/app/build.gradle — verify this exists and runs
project.ext.sentryCli = [
    logLevel: "debug",  // temporarily add this
    flavorAware: false
]

apply from: "../../node_modules/@sentry/react-native/sentry.gradle"
```

---

## Step 3: Common Root Causes & Fixes

### Problem 1: `SENTRY_AUTH_TOKEN` Not Reaching the Build

EAS build environment variables require explicit declaration:

```json
// eas.json
{
  "build": {
    "production": {
      "env": {
        "SENTRY_AUTH_TOKEN": "your-token-here"
      }
    }
  }
}
```

```bash
# Better approach — use EAS Secrets (not plaintext in eas.json)
eas secret:create --scope project --name SENTRY_AUTH_TOKEN --value sntrys_xxx
```

Then verify the secret is scoped to the right build profile:

```json
// eas.json — reference the secret
{
  "build": {
    "production": {
      "env": {
        "SENTRY_AUTH_TOKEN": "$(SENTRY_AUTH_TOKEN)"  // NOT needed — EAS injects secrets automatically
      }
    }
  }
}
```

> **Note:** EAS Secrets are injected automatically — you don't reference them in `env`. If you're putting the token in `env`, you're using a plaintext variable, not a secret.

### Problem 2: Wrong Org/Project Slug

```bash
# Verify your sentry.properties file exists and is correct
cat ios/sentry.properties    # or android/sentry.properties
cat sentry.properties        # root level fallback

# Should contain:

defaults.project=your-project-slug
auth.token=...  # only if not using env var

### Problem 3: Hermes Source Maps Need Extra Step

Hermes compiles JS → bytecode, so you need **two-stage source map composition**:

```bash
# If doing manual upload, you need BOTH maps composed:
npx react-native bundle \
  --platform android \
  --dev false \
  --entry-file index.js \
  --bundle-output /tmp/index.android.bundle \
  --sourcemap-output /tmp/index.android.bundle.packager.map

# Then compose with Hermes's own map:
node node_modules/react-native/sdks/hermesc/compose-source-maps.js \
  /tmp/index.android.bundle.packager.map \
  /tmp/index.android.bundle.hbc.map \        # generated by Hermes compiler
  -o /tmp/index.android.bundle.map           # this is the final map to upload

# @sentry/react-native's sentry.gradle does this automatically
# but only if the gradle hook is properly applied
```

Based on the note from past work on this exact scenario: **the upload did not fail** — you're just looking in the wrong place.

## Why the Releases list misleads you here

`@sentry/react-native` on Hermes uses **debug-ID-based artifact bundles**, which are completely decoupled from the classic Sentry "releases" concept. The `bundleId@version` release entry you're expecting simply does not get created by this upload path. The git-SHA releases you see are from your backend's `@sentry/node` / `sentry-cli` path — a different system entirely.

## How to actually verify

Query the artifact bundles endpoint instead:

```
GET /api/0/projects/{org}/{project}/files/artifact-bundles/?sortBy=-date_added
```

What confirms a successful upload:
- A bundle timestamped to your build time
- `fileCount: 2` — the Hermes JS bundle and its source map

These two files are exactly what you need for Sentry to symbolicate Hermes stack traces.

The **releases list** and the **`files/source-maps/` endpoint** both show classic release archives — neither is where the RN bundle appears, and checking either will falsely suggest the upload failed.

## What can actually cause a silent no-op

The one real failure mode to rule out: check your EAS build log and confirm it shows `SENTRY_AUTH_TOKEN` was loaded from the environment. The Sentry plugin silently skips the upload entirely if the token is absent, with no error. If the token was present in the log and your artifact bundle endpoint shows a fresh 2-file bundle at build time, the upload succeeded.
```

## Diagnosing the Problem

This is a classic **Jest configuration collision** caused by a module that pulls in code with incompatible transform/environment requirements at import time. Here's exactly what's happening and how to fix it properly.

---

## What's Actually Happening

### The Root Cause Chain

```
New test imports validation-schemas
  → validation-schemas imports (e.g.) joi / zod / yup
    → That package ships untranspiled ESM or uses syntax
      Jest's current transform config can't handle
        → Jest throws "Invalid configuration" / "SyntaxError"
          → Entire worker process crashes
            → Whole suite reports "failed to run"
```

The reason it passes locally but fails in CI is almost always one of:

| Local | CI |
|---|---|
| Node 20 (supports more syntax natively) | Node 18 or 16 |
| `node_modules` cached from an older install | Clean install pulls latest package version |
| `.env` sets `NODE_OPTIONS=--experimental-vm-modules` | CI has no such variable |
| Local Jest config is picked up from a parent dir | CI runs from repo root with a different config |

---

## Step-by-Step Diagnosis

### 1. Reproduce the exact CI error locally first

```bash
# Blow away cache to match CI's clean state
npx jest --clearCache
rm -rf node_modules/.cache

# Run with the same NODE_ENV CI uses
NODE_ENV=test npx jest --no-coverage 2>&1 | head -60
```

### 2. Find the actual offending module

```bash
# Jest will tell you which file it choked on - look for lines like:
# "Jest encountered an unexpected token"
# "SyntaxError: Cannot use import statement in a module"
# Usually followed by a file path inside node_modules/
```

### 3. Check what your validation-schemas module imports

```bash
# Trace the full import chain
node --input-type=module <<'EOF'
import { createRequire } from 'module';
// or just:
EOF

# Faster: check package.json of the suspect lib
cat node_modules/zod/package.json | grep -E '"main"|"module"|"exports"|"type"'
```

---

## The Fix (Robust, for the Whole Suite)

### Fix 1: Transform ESM packages that Jest can't handle natively

This is the most common fix. In your `jest.config.js`:

```js
// jest.config.js
/** @type {import('jest').Config} */
module.exports = {
  // ... your existing config

  // This is the critical section:
  // List every package that ships ESM and needs transpilation
  transformIgnorePatterns: [
    // The default is ["/node_modules/"] which tells Jest:
    // "never transform anything in node_modules"
    // We need to EXCLUDE certain packages from that ignore list:
    '/node_modules/(?!(' + [
      'zod',           // add whichever package(s) are actually failing
      'joi',
      'uuid',          // uuid v9+ is ESM-only
      'nanoid',        // ESM-only
      'your-other-esm-package',
    ].join('|') + '))',
  ],
};
```

**Why this works:** `transformIgnorePatterns` is a list of patterns where Jest *skips* transformation. The regex above says "ignore everything in node_modules EXCEPT these specific packages" — so Babel/SWC will transpile them to CJS that Jest can consume.

---

### Fix 2: Ensure your Babel config handles the right syntax

```js
// babel.config.js  (note: .babelrc does NOT apply to node_modules, babel.config.js does)
module.exports = {
  presets: [
    [
      '@babel/preset-env',
      {
        targets: {
          node: 'current', // transpile only what current Node doesn't support
        },
      },
    ],
    '@babel/preset-typescript', // if you use TS
  ],
};
```

**Critical distinction:** `.babelrc` / `.babelrc.js` only applies to files within the same package. For transforming `node_modules`, you **must** use `babel.config.js` (project-wide config).

---

### Fix 3: Pin Node versions to match between local and CI

```yaml
# .github/workflows/test.yml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version-file: '.nvmrc'  # single source of truth
          cache: 'npm'
```

```bash

20.11.0
```

```bash
# .node-version  (for tools that prefer this format)
20.11.0
```

This eliminates the entire class of "works on my machine" Node version drift.

---

### Fix 4: Lock down the Jest environment explicitly

Don't let Jest guess the environment. Be explicit per-file or globally:

```js
// jest.config.js
module.exports = {
  // Explicit environments prevent surprises
  testEnvironment: 'node', // for unit tests with no DOM

  projects: [
    // If you have both unit and browser tests, split them:
    {
      displayName: 'unit',
      testEnvironment: 'node',
      testMatch: ['<rootDir>/src/**/*.unit.test.{ts,js}'],
      transformIgnorePatterns: [
        '/node_modules/(?!(zod|uuid|nanoid)/)',
      ],
    },
    {

## What's happening

Your new test imports `validationSchemas`, which transitively requires `config/environment.js`. That module calls `validateConfig()` at the bottom of the file — at **require-time**, not lazily. It throws `Invalid configuration` when `JWT_SECRET` and `DATABASE_URL` are unset.

**Why it passes locally but fails in CI:**

- Locally, `dotenv.config()` finds `Backend/.env` and loads those variables before the validation runs. The check passes silently.
- In CI's unit job, there is no `.env` file. `dotenv.config()` loads nothing. The validation fires on empty env vars and throws. Because this happens during module loading — before any test even starts — Jest reports the entire suite as "failed to run", not just the one test.

This is a latent gap: every previous unit test happened to never pull in the config module, so it was never hit. Your test was the first one to cross that boundary.

---

## The robust fix: make `tests/setup.js` hermetic

The correct fix is **not** to patch the one test, mock the module, or skip the validation. It is to ensure the unit test environment itself always provides the minimum env vars that config validation requires. You already have a `tests/setup.js` wired as `setupFilesAfterEnv`; extend it:

```js
// tests/setup.js

// --- Hermetic env vars for unit tests ---
// These are set BEFORE any module is required by any test.
// The ||= guard means real CI integration values (if present) are never overwritten.
// Unit tests never open a real DB or sign real tokens, so these dummies are inert.
process.env.JWT_SECRET        ||= 'test-jwt-secret-unit-tests-only';
process.env.DATABASE_URL      ||= 'postgresql://test:test@127.0.0.1:5432/test_db';

// Already present — shown for context, do not duplicate:
// process.env.EMAIL_ENABLED = 'false';
```

### Why `||=` and not a plain assignment

```js
// Plain assignment — WRONG for this use case
process.env.JWT_SECRET = 'dummy';
// Silently overwrites a real value an integration job already set.
// Unit jobs: fine. Integration/e2e jobs running in the same runner: broken.

// Nullish-coalesce assignment — CORRECT
process.env.JWT_SECRET ||= 'dummy';
// If the var is already set (real CI secret, Docker compose value, etc.), leave it alone.
// If it is absent (unit-only CI job, local run without .env), supply the dummy.
```

## Why this fix is scoped correctly

| Approach | Problem |
|---|---|
| Mock `config/environment` in the one test | Fixes one test, next test that imports config breaks again |
| Add `dotenv` call pointing at a test `.env` file | Adds a file that must be kept in sync; still fragile |
| Wrap `validateConfig()` in a try/catch in the module | Silences real misconfiguration in production |
| **Hermetic defaults in `tests/setup.js`** | **Fixes the whole class once; inert in integration jobs; self-documenting** |

The setup file runs before any test module is loaded, so the env vars are present by the time `config/environment.js` evaluates `validateConfig()`. Every future test that transitively imports config — whether you intended it to or not — will work correctly in CI without any per-test intervention.

The fix is always: make the test environment supply the minimum required values unconditionally, using guards that don't break integration jobs.
